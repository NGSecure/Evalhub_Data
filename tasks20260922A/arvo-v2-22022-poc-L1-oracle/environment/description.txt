nDPI's stream-classification engine (AFL packet-fuzzing harness, ASan build): a heap-buffer-overflow read occurs while nDPI is trying to identify a TCP flow as the NATS messaging protocol. Root cause: the detector first locates a protocol-keyword match somewhere inside the TCP payload buffer, then wants to keep searching forward from that match position for a trailing line terminator, so it computes "how many bytes remain until the end of the payload" via pointer arithmetic — subtracting the match pointer's address from the payload start pointer's address, i.e. the two operands are in the wrong order. Since the match position is normally at or after the payload start, this subtraction is computed backwards and, cast to an unsigned integer, underflows to a huge intermediate value. That intermediate value is then itself subtracted from the (small) actual payload length in a second unsigned subtraction; because unsigned arithmetic wraps modulo 2^64, this second underflow does not compound the error into something astronomically large — the two wraps effectively cancel, so the final "bytes remaining" value passed down ends up only modestly larger than the true remaining length (roughly double the match offset past the payload start), not a near-maximum value. That modestly-too-large bound is passed as a trusted limit to a bounded string-search helper used elsewhere throughout the library, which walks the buffer one byte at a time, decrementing the bound and only stopping early if it happens to hit a NUL byte; with the bound slightly overstated, it walks a short, bounded distance past the end of the heap-allocated payload buffer, which is enough for AddressSanitizer to catch the out-of-bounds read at the buffer's edge.
