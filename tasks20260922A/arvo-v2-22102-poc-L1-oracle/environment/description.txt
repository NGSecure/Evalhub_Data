PcapPlusPlus's packet-parsing fuzz target (ASan build): reading a captured packet whose UDP payload is treated as DNS triggers a 2-byte heap-buffer-overflow read while decoding one resource record's fixed-length metadata that follows the record's variable-length, possibly-compressed domain name. Root cause: the routine that decodes a resource record's encoded name only bounds-checks the name's own label bytes against the remaining packet buffer, so it can return a name length that leaves fewer than the required type/class/TTL/record-length-field bytes before the buffer's end; the code path that computes the record's total on-wire size then unconditionally reads the fixed 2-byte record-length field located right after the name's fixed-size type, class and TTL fields, before any check exists that the whole record actually fits inside the packet -- so for a resource record whose encoded name runs almost to the end of a short buffer, that read lands past the allocation, and only afterward does the caller discover (too late) that the resource's computed size exceeds the remaining packet data and would have been rejected.
