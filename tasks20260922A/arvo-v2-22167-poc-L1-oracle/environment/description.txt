nDPI's generic HTTP-style line/header parser (reached here through the Steam protocol detector, ASan build under the AFL/libFuzzer packet-reader harness) scans a TCP payload for the end-of-headers CRLFCRLF ("\r\n\r\n") marker and, once it finds one, tries to stash a handful of the bytes right after that marker into a small fixed-size per-flow buffer for later protocol sniffing. It computes how many payload bytes remain past the marker as a plain subtraction (total payload length minus the offset just past the marker) and feeds that raw result straight into a min-style clamp against the fixed buffer size, without first checking whether the subtraction was actually negative. When the CRLFCRLF marker sits close enough to the tail of the payload that the offset just past it is already at or beyond the payload's real length, the intended "bytes remaining" value is negative, but because the subtraction is evaluated in unsigned arithmetic before that clamp, it instead wraps around into a huge unsigned number; the clamp then compares that huge number against the small fixed buffer size and returns the buffer size itself, as if it were a legitimate small positive count. The code then copies that many bytes starting from the already out-of-bounds offset into the per-flow buffer, reading past the end of the heap-allocated payload and producing an 8-byte heap-buffer-overflow read.
