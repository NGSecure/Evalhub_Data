nDPI (AFL/ASan fuzz target for the packet-processing/protocol-detection pipeline, reached here through the SMTP dissector's per-packet line scan): while walking a TCP payload byte-by-byte looking for a CRLF end-of-line marker, once one CRLF pair is found the code immediately probes two bytes further ahead with a second, fixed-size 2-byte read to check whether a second CRLF follows right after it (testing for a blank "\r\n\r\n" line that would terminate a header block). Root cause: the surrounding loop only guarantees enough payload remains for the first CRLF's own 2-byte read (it bails out early if fewer than two bytes are left from the current position), but adds no matching bounds check before the second, farther-ahead 2-byte read; when the first CRLF happens to sit at the very last two bytes of the payload, that second read starts right past the end of the heap buffer, producing a heap out-of-bounds read.
