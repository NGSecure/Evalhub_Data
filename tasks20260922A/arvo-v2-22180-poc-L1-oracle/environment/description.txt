Fluent Bit's logfmt log-line parser (ASan build, same fuzz target family as a sibling crash id in this batch) hits a distinct one-byte heap-buffer-overflow read, this time inside the numeric-escape decoder that the value-unescaping routine hands control to once it recognizes an octal, hex, or Unicode-style escape introducer -- as opposed to one of the fixed single-character escapes such as newline or tab. That decoder consumes as many valid digit characters as its escape kind allows by repeatedly testing whether the next character still looks like a digit, but the helper was never given any notion of how many bytes remain in the caller's buffer. When the digit run following the escape introducer happens to end exactly at the input's last valid byte (for instance, a single octal digit sitting right at the buffer's tail), the digit-scan condition still dereferences one more character beyond that point to check whether the run continues, landing one byte outside the heap allocation. This fires only once execution has already passed the outer unescaping loop's own end-of-buffer handling and descended into this deeper digit-scanning helper, and only when the trailing bytes form a numeric-style escape rather than a bare trailing backslash -- a different code path and a different missing bounds check from the sibling crash in this same source file.
