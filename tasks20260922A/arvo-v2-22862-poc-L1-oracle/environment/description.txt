PcapPlusPlus's packet-parsing fuzz target (ASan build): dissecting a captured frame whose Linux-cooked-capture (SLL) link-layer header leaves only a single trailing byte as payload, where that leftover byte's ethertype happens to select the PPPoE Discovery protocol, triggers a heap-buffer-overflow READ of 2 bytes. Building the PPPoE discovery layer object from that near-empty remainder unconditionally reads a 16-bit length field at a fixed byte offset inside the expected multi-byte PPPoE header, assuming the full header is present in the data handed to it; but the underlying raw-packet allocation captured from the pcap file ends only one byte past the SLL header, so the read lands several bytes beyond the end of that heap buffer. Nothing on the path from the SLL header's protocol dispatch to the discovery-layer object's construction first confirms that enough trailing bytes remain to cover a full PPPoE header before that length field is read.
