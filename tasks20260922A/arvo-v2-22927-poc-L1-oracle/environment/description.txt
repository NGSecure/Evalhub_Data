muparser's expression set/evaluate fuzz target (ASan build) hits a heap-buffer-overflow read of 8 bytes, located immediately before the start of a heap-allocated runtime evaluation-stack buffer, while the built-in variadic summation callback dereferences the very first element of the argument array it was handed. Root cause: the expression compiler determines how many values a variable-argument function call will receive by counting the comma-separated sub-expressions written inside its parentheses at parse time. When one of those comma groups is actually the "then" branch of an embedded ternary conditional operator, and the "then" and "else" branches contain different numbers of comma-separated values, the compiled instruction stream still records the argument count taken from parsing (the larger branch), even though only one branch's push operations actually execute at evaluation time, because the untaken branch's pushes are skipped by a conditional jump. When the runtime evaluator later processes that instruction, it walks the stack index backward by the recorded (but now too-large) argument count to locate where the function's arguments begin, and does so without verifying the resulting index is still within the buffer, so the index underflows past the start of the allocation and the summation loop's first read lands one 8-byte slot before the buffer.
