muparser's set_eval_fuzzer triggers an 8-byte heap-buffer-overflow READ inside ParserBase::ParseCmdCodeBulk, reached through ParseCmdCode from ParserBase::ParseString(), when the parser evaluates a formula whose top-level value is a long comma-separated list of empty string literals terminated by a trailing bare numeric literal (e.g. dozens of repetitions of an empty-string token separated by commas, followed by a plain number).

Root cause: ParseString() first calls CreateRPN(), which walks the token stream — applying pending operators, the ternary if/else construct, and function calls via an internal work-stack pair (a value stack and an operator stack) — to compile a compact RPN bytecode, and, based on what that compile-time walk believes the maximum concurrent stack depth will be, allocates a fixed-size runtime array of doubles that the bytecode interpreter will index into. ParseCmdCodeBulk then executes that compiled bytecode against real input data, walking the array with an internal stack-index counter that increments on every value push. For this crafted input, the compile-time depth estimate computed while walking the long string-literal-then-number list undercounts the actual number of slots ParseCmdCodeBulk touches by exactly one double (8 bytes): the top-level comma-separated list mixes many string-typed sub-results with a single trailing numeric sub-result in a way the compile-time work-stack bookkeeping does not fully reconcile, so the interpreter's final index computation reads one slot past the end of the allocated runtime array — landing exactly 8 bytes beyond the end of the heap block, matching the reported "READ of size 8" one element past a 256-byte (32-double) allocation.

What the fix does: it hardens the internal work-stack handling used while CreateRPN walks the token stream and applies pending operators/functions/the ternary construct — replacing a custom stack wrapper (whose "pop" combined "read the top element" and "remove it" into a single call) with the standard library stack type used directly, split at every call site into an explicit "read top" step followed by a separate "remove" step, plus added not-empty checks/hard assertions guarding each of those removals in the ternary if/else handling and the function-application path that were previously only guarded loosely. Alongside this, two new regression tests were added that encode the exact crashing pattern (a long list of empty-string literals ending in a number, and a short 3-item variant of the same shape), and both are now asserted to make muparser raise an "unexpected string" parse error rather than compiling successfully. In other words, after the fix this string/number-mixed top-level list is rejected up front during parsing/compilation, so the RPN bytecode that previously caused the runtime interpreter to read one double past the end of its execution-stack buffer is never produced or executed.
