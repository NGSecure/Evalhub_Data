c-blosc2's decompression entry point parses an incoming chunk's header before decompressing it, and when the header's shuffle/bitshuffle flag combination selects the newer extended-header layout whose own flag byte additionally advertises an embedded compression dictionary, the parser locates the 4-byte dictionary-size field at an address computed purely from two attacker-controlled header integers (the declared uncompressed size and the declared per-block size, whose ratio yields a block count) added on top of the fixed per-block start-pointer table, with no check that this computed offset still lies inside the actual bytes of the compressed input buffer that was handed to the routine. A short, crafted chunk that declares a small block size (hence a large block count) relative to its own true length pushes that computed address past the end of the real input allocation and into unrelated, freshly heap-allocated memory that has not yet been written by anything, so the 4 bytes read back into the dictionary-size variable are uninitialized garbage rather than attacker data -- caught by MemorySanitizer as a use-of-uninitialized-value rather than an out-of-bounds crash, because the read still lands inside mapped heap (in the reported trace, inside a same-sized scratch buffer the fuzz harness had just malloc'd for the decompression output, not yet written to). Root cause: the legacy public decompression call exercised by the fuzz target never threads the actual length of the compressed source buffer into the header-parsing logic at all, so nothing downstream can validate any header-derived offset -- the end of the block-start-pointer table, the dictionary-size field itself, or the dictionary payload that would follow it -- against the buffer's real size; every such offset is trusted at face value from the chunk's own self-reported, unauthenticated size fields.
