nDPI's IAX (Inter-Asterisk eXchange) protocol dissector, invoked while classifying a UDP flow, walks a sequence of variable-length information elements (IEs) packed into the call-setup packet's payload, and on a malformed/truncated packet reads one byte past the end of the heap buffer holding that payload.

Root cause: the dissector starts at a fixed offset into the payload and loops, and before processing each IE it checks only that the current offset is still strictly less than the payload length before continuing. But the very next thing the loop body does is dereference the byte immediately after that offset (the IE's own length field) in order to compute how far to advance for the next iteration. The bounds check therefore validates only the position of the IE's *type* byte, not the position of the *length* byte read right after it. When the current offset lands exactly on the last valid byte of the payload (i.e., one byte before the payload actually ends), the "is there at least one more byte" check still passes, so the loop body executes and reads the length-field byte at offset+1, which is one byte past the allocated payload buffer — a 1-byte heap out-of-bounds read. This matches the observed crash: a 1-byte READ landing exactly at the byte immediately following the payload allocation.

On fix_commit: the patch tightens exactly this loop-continuation check so that it also accounts for the extra byte the loop body is about to read (i.e., the break condition now requires the offset *plus one* to still be within the payload, not just the offset itself). This directly closes the specific off-by-one gap described above — the check now fails (and the loop breaks) one iteration earlier whenever continuing would have dereferenced the trailing out-of-bounds byte. The function and file touched by the fix are the same ones present in the crash backtrace, and no unrelated code is touched, so the fix_commit is a credible, well-targeted match for this crash (no correction needed).
