LibRaw (UBSan build): a crafted Fuji raw file drives the demosaic engine's hot-pixel-suppression pass into reading one element past the end of each pixel's small three-channel float working buffer. During raw-to-image conversion, the demosaic engine first builds a per-pixel three-channel float array from the file's own reported color-filter-array layout; a value that stands for a rarely-used fourth filter code is remapped down to the ordinary green channel wherever that buffer is populated. A later pass that looks for and patches individual "stuck" pixel values re-derives, independently and per scanline, which color channel is expected at the very first non-green sample position on that row, using the same raw per-row filter-array query but without applying that same fourth-code-to-green remapping; it then also flips that channel value (red-to-blue and back) to reach the other non-green channel when checking neighboring samples on alternate rows. For an ordinary two-color-per-row Bayer-style sensor layout this row-parity assumption always holds, but a corrupted or crafted color-filter-array description can make the position this pass expects to be a definite red-or-blue sample instead report green, or the sensor's rarely used fourth filter code; flipping that unexpected value lands one slot past the last valid index of the three-channel float array, producing the out-of-bounds read UBSan reports. The commit on record as this bug's fix only tightens validation of floating-point/deflate DNG bit-depth metadata inside the DNG-specific decoder-selection logic used during file-format identification; it has no connection to the raster-array color-filter bookkeeping in the demosaic stage described above, and a native Fuji raw file (as this PoC is) never reaches the DNG-specific branch that commit modifies in the first place.
