PcapPlusPlus (ASan build), the packet-parsing fuzz target: when the dissector recognizes UDP payload data as a GTPv1 message and builds a GTPv1 layer over it, the check that gates this recognition accepts buffers far shorter than the fixed GTP header actually needs, so a GTPv1 layer can be constructed over data that never held a complete header in the first place. Computing that layer's header length still walks the optional chain of GTP-U extension headers as if a well-formed header were present. Each extension stores a one-byte "total length" field (counted in 4-byte units) that, after being clamped against the number of bytes the code believes remain for that extension, is used to locate the trailing byte naming the type of the next extension in the chain. Because the chain's per-extension remaining-length bookkeeping is derived from an initial buffer size that was never validated against the true minimum header size, the computed offset for that trailing byte can still land past the end of the actual heap allocation backing the captured packet, and dereferencing it to read the next-extension-type value performs a one-byte out-of-bounds heap read — reported by AddressSanitizer as a heap-buffer-overflow READ of size 1 at an address described as a "wild pointer," far from any valid allocation.
