Apache Arrow's C++ array-concatenation path (ASan build, reached from the IPC stream-reader fuzz target while it merges an incoming dictionary-delta batch into an existing dictionary) triggers a heap-buffer-overflow read of 4 bytes when merging the variable-length offsets buffers of a binary/string-typed array. The internal helper that copies one input array's offsets into the merged output buffer unconditionally reads the very first element of that input's offsets buffer, using it both to seed the value-range bookkeeping for the underlying data buffer and to compute the adjustment applied to every offset written into the destination — it never checks whether that buffer actually contains any elements first. Arrow's own array-validation rules permit a zero-length binary/string array to carry a completely empty (zero-byte) offsets buffer, omitting the usual terminating sentinel offset that a non-empty array would have. When such a zero-length array turns up as one of the inputs being merged — which can happen while an IPC reader incrementally rebuilds a dictionary from a delta record batch — the unconditional read lands one element past the end of that empty buffer's allocation, producing the observed out-of-bounds read.

The fix adds an explicit guard at the top of that helper: if the input's offsets buffer is empty, the value range is short-circuited to (0, 0) and the function returns immediately, before the first element is ever dereferenced. It separately hardens the later per-offset adjustment arithmetic to use a checked/unsigned-safe addition instead of plain signed addition, guarding against undefined behavior when adding an adjustment to not-yet-validated offset values — a related but secondary hardening, since the crash itself is the out-of-bounds read guarded by the new empty-buffer check, not the arithmetic. The fix touches exactly the array-merging source file the crash trace points to and the same offset-copying routine identified as the crash site, so it is a credible, on-target fix for this crash.
