LibRaw (MSan build): a truncated, malformed Fuji-compressed raw file causes the strip decoder to consume an uninitialized block-size value. Before decoding, the loader allocates a small per-block size table sized according to the file's own declared block count and reads that many bytes' worth of size entries directly from the file into the table; the buffer is allocated with a plain, non-zeroing allocator, and the code never checks whether the file actually contained enough bytes to fill the whole table in the first place. For a file that declares a given number of compressed blocks but is too short to actually supply size data for all of them, the tail of this table is left holding whatever uninitialized heap bytes were present at allocation time; those bytes are nonetheless reinterpreted as a valid block byte-count and copied back into the same table entry. That per-block byte-count then flows, unexamined, into the per-block decode-state setup routine, where it is combined with the remaining file size to compute how many bytes are still available to read for that block -- an uninitialized value feeding directly into that computation, which is what MemorySanitizer flags. The commit recorded against this bug only tightens bit-depth/sample-format validation for the floating-point and deflate variants of DNG's own raw-decoder-selection logic during file-format identification; it makes no change anywhere in the Fuji-compressed block-size or decode-state setup path described above, and this PoC (which begins with the native Fuji raw-format signature, not a DNG/generic-TIFF one) never reaches the DNG-specific branch that commit touches in the first place. A large, unrelated whole-file restructuring of the Fuji-compressed decoder that landed several months before this bug's recorded fix date was also checked and found to preserve the identical missing-length-check pattern verbatim, so it does not explain the fix either; the change that actually fixed this bug could not be conclusively identified.
