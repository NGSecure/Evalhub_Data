muparser's expression compiler fails to validate the operand types produced by a ternary conditional (`?:`) operator, letting a string-typed branch result be folded into the compiled program as if it were numeric, which later causes a heap out-of-bounds read one 8-byte slot before the start of the runtime evaluation stack when that program is executed.

During compilation, each branch of a ternary conditional is resolved on an internal value stack, and the surviving branch's value is what actually gets carried forward into the emitted instruction stream. When the "then" branch evaluates to a number but the "else" branch evaluates to a string constant (for example a quoted, parenthesized empty string), the ternary-resolution step does not check that both branches share the numeric type before accepting one of them as the ternary's result. It happily folds the string-typed value in exactly as it would a numeric one, so the emitted instruction stream ends up under-counting how many numeric intermediate values this sub-expression will actually leave behind at runtime.

When the resulting (miscompiled) program is executed, the interpreter walks the instruction stream while tracking an integer stack index into a pre-sized buffer of intermediate double values: the index is advanced whenever an instruction pushes a numeric value, and it is decremented (with the now-top slot read back) whenever a binary numeric operator executes. Because the ternary's malformed sub-expression left one fewer numeric value on the stack than a subsequent binary numeric operator expects to consume, that operator's decrement drives the stack index below zero, and the following read lands one double-sized slot before the start of the heap-allocated buffer. This is an out-of-bounds *read* caused by the index under-running the buffer's low end, not an overrun past its high end.

This is only reachable when a ternary whose false branch is a parenthesized string literal is itself fed into an enclosing binary numeric operator (so the operator actually needs to consume the ternary's under-counted result); a ternary whose branches are both consistently numeric, or whose result is never combined with a further numeric operator, does not exhibit the bug.

The fix adds an explicit type check immediately after each branch value is popped off the ternary's internal value stack during compilation: if either branch's value is not the numeric type, compilation now aborts immediately with a parse-time "unexpected string" error instead of silently continuing to fold the mismatched branch. This closes the gap by rejecting the ill-typed ternary before any under-counted instruction stream can ever be emitted, so the runtime stack index never gets driven negative in the first place.

Note on provenance: the fix commit's own message and changelog entry cite a different (but closely related, same-day) fuzzer-reported issue number rather than this crash's issue number. However, the commit's timestamp falls squarely inside the build-revision window that was independently recorded as the point where this specific crash's reproducer stopped reproducing, and the check the commit adds sits exactly on the ternary-resolution code path that this crash's call stack passes through (bulk/vectorized program evaluation invoked from the top-level expression-parsing entry point). Both the timing and the mechanism line up, so the recorded fix commit is treated as correct for this crash despite the mismatched issue number in its own commit message — this looks like two duplicate fuzzer reports of the same underlying gap fixed by one shared commit, not a misattributed fix.
