YARA's rule compiler (fuzzed via rules_fuzzer, MSan build): an uninitialized-value read occurs while computing a hash-table key for a plain string literal that the parser extracts out of a compiled regular-expression AST during a string declaration (e.g. a rule string like `$s = "ab"` with no wildcards or operators). Root cause: the extraction step allocates a small buffer sized exactly for the literal's characters plus one extra trailing byte reserved for a NUL terminator, then fills the character bytes by walking the AST's literal nodes back-to-front using a local counter that is decremented down to zero as each character is placed into the buffer. Afterward, that same already-exhausted counter is reused to write the terminator byte, so for any literal built from two or more concatenated single-character nodes, the terminator ends up written to the buffer's very first byte instead of the one byte reserved past the last character — clobbering the first extracted character while leaving the actual last, reserved byte of the allocation never written by anyone. This buffer is then handed, together with a byte count that deliberately includes that reserved terminator byte, to a general-purpose hashing routine used to deduplicate the compiler's internal string pool; the routine reads every byte of the buffer up to and including that count, so its final byte access touches memory nobody initialized, and MemorySanitizer reports the use there. A one-character literal takes a different code path where the counter is never decremented, so only literals assembled from two or more characters trigger the bug.
