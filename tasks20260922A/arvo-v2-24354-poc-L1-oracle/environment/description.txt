ClamAV's OLE2/VBA macro-project directory-stream parser (reached from cli_scanole2 -> cli_vba_scandir_new while scanning an embedded VBA project inside an OLE2/ZIP document) triggers a heap-buffer-overflow READ inside iconv() when converting one of the project's module-name strings from UTF-16LE to UTF-8. Root cause: while walking the MS-OVBA dir-stream records to find the module-stream-name-unicode record, the parser reads a 4-byte length field straight out of the untrusted, previously-decompressed dir buffer and passes it unchecked as the byte count into the UTF-16-to-UTF-8 conversion helper, without first verifying that the length does not exceed the number of bytes actually remaining in that buffer. A guard that is meant to skip the conversion call entirely when there is nothing to convert instead tests a stale length variable left over from an earlier, unrelated record rather than this record's own freshly-parsed length, so it is effectively decoupled from the value that actually gets passed to the conversion helper and cannot reliably block a large, attacker-controlled length from reaching it. Because the dir buffer produced by decompressing the VBA project stream is typically only on the order of a kilobyte, but the crafted length field can be as large as a 32-bit value, the conversion call ends up asking iconv() to read gigabytes of "UTF-16" input starting inside that small heap allocation, running far past its end before AddressSanitizer catches the out-of-bounds read.
