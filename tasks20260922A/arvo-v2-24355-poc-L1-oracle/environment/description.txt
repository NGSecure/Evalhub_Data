muparser's set_eval_fuzzer triggers an 8-byte heap-buffer-overflow READ inside ParserBase::ParseCmdCodeBulk, reached from ParserBase::Eval() through ParseCmdCode()/ParseString(), when evaluating a formula whose top level is one long comma-separated list: dozens of bracketed, otherwise content-free string literals -- e.g. `("...")`, `("...")`, `("...")`, ... -- followed by one trailing comma-separated arithmetic sub-expression mixing numeric literals, arithmetic operators, and function calls (sqrt, max).

Root cause: ParseString() first calls CreateRPN(), which walks the token stream once using two compile-time counters that are supposed to stay consistent with each other. The first is an outer "argument count" that is incremented by one every time a comma is seen at the outermost nesting level, regardless of what kind of value preceded it. The second is the RPN bytecode builder's own running/maximum stack-depth counter, which only advances when a token actually pushes a numeric value onto the runtime evaluation stack -- a plain number, a variable, or the result of applying an operator/function. A bare string literal wrapped only in parentheses, with no enclosing function name and no operator ever applied to it, is recorded solely on a separate compile-time value-type stack used for syntax bookkeeping; it never triggers a "push" event, so it contributes nothing to the bytecode builder's max-depth counter. After CreateRPN finishes walking the tokens, the fixed-size runtime array of doubles that ParseCmdCodeBulk will index into is sized using only that max-depth counter -- while the value ParseCmdCodeBulk later reads out as "the final result" is the independently-tracked outer comma counter. Because this crafted formula's top level is overwhelmingly made of parenthesized bare-string items that inflate the comma counter without ever touching the depth counter, the comma counter ends up exactly equal to the total size (in doubles) of the array CreateRPN just allocated once the trailing real arithmetic term is folded in -- so the final read at the end of evaluation lands exactly one double (8 bytes) past the end of that heap block, independent of what the trailing arithmetic actually evaluates to.

What the fix does: the two committed hunks do not touch CreateRPN or the bytecode builder's stack-depth accounting at all. Instead they close off one specific way this ClusterFuzz-minimized input manages to reach that state: the tokenizer's "skip insignificant whitespace before the next token" loop previously treated any byte in the 0x01-0x20 range as silently skippable with no further validation; the fix narrows this by raising an "invalid characters" parse error the moment a byte in the 14-31 sub-range is about to be skipped that way. A separate, much coarser guard in SetExpr -- which only rejected an expression if *every single character* in it failed the "is printable" test -- is removed at the same time, since it could never have caught this input anyway (only a handful of its roughly 1200 bytes are non-printable; the rest is ordinary parser syntax).

fix_commit assessment: partially credible, with a concretely demonstrated gap (see the fix_commit_correction_note added to crash.json). Rebuilding both the vulnerable and "fixed" sources from src-vul.tar.gz/src-fix.tar.gz and replaying the exact recorded poc reproduces this id's recorded differential exactly: the vulnerable build crashes identically (same heap-buffer-overflow, same source line), and the fixed build now rejects the input up front with an "invalid characters" parse exception -- because the poc happens to use a byte in the 14-31 range as filler between every top-level comma and the following "(". However, substituting that one filler byte throughout with an ordinary space (0x20, a byte the new check does not touch) reproduces the identical heap-buffer-overflow, at the identical source line, in *both* the vulnerable build and the nominally-fixed build (verified locally by rebuilding and replaying both variants). This shows the recorded fix_commit patches only the incidental byte-encoding this particular minimized reproducer happens to use to slip past SetExpr's old blanket check -- not the underlying comma-counter/stack-depth-counter mismatch that is the actual root cause of the overflow. It is nonetheless the correct commit to record in this crash.json entry, since it is exactly what makes the *recorded byte-for-byte poc* stop crashing, matching both this id's own differential fields and the upstream OSS-Fuzz "verified as fixed" record tied to the same testcase -- but it should not be read as evidence that the deeper stack-accounting bug itself was fixed.
