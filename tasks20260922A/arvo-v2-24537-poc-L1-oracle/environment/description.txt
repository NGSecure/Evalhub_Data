RDKit's V2000 molfile-to-mol streaming fuzz target (libFuzzer, ASan build): a stack-buffer-overflow read occurs while parsing a query atom-list line embedded in a V2000 CTAB's atom block -- specifically the older, compact encoding that this atom block supports for such lines (the same block also accepts a longer, newer-style encoding of the same concept, handled by separate code). The compact-format parser first pulls a fixed-width atom index off the front of the line and resolves it to an existing atom, then inspects a single character a little further along the line to decide whether the resulting query should be negated ('T') or not ('F'). When that character is neither 'T' nor 'F', the parser takes an error path that builds a diagnostic message quoting "the offending character" -- but the column offset used to pull that character out of the line was written for the *other*, longer-format atom-list parser, whose analogous flag character legitimately sits much further into its (longer) line, rather than for this compact format's own, much earlier flag column. So a short, compact-format line that gets far enough to reach this check (its fixed-width atom index parses cleanly and stays in range) but carries a bogus flag character causes the diagnostic-message code to index several bytes past the end of the line string. Because that line is a short local string living inline on the caller's stack frame (small-string-optimization storage, not a heap allocation), reading past its stored characters shows up as a stack-buffer-overflow rather than a heap one.
