assimp's Doom 3 / MD5 mesh importer (ASan build, libFuzzer harness) triggers a 1-byte heap-buffer-overflow read while a shared comment-stripping helper scans a text buffer that was just heap-allocated to hold the exact contents of the loaded mesh file plus its NUL terminator. The outer scan loop tests whether the byte at the current position is non-NUL only once, at the top of each pass; within a pass, before checking for a comment marker, a separate inner loop skips over an open quote span by walking the pointer forward one byte at a time via a post-increment dereference, advancing until it finds a closing quote or hits the NUL. Because that post-increment always fires -- even on the very step where it reads the NUL -- an opening quote that is never closed before the end of the file leaves the pointer sitting exactly one byte past the terminating NUL (i.e. one byte past the end of the allocation) once the inner loop exits, with no re-check of that new position before control falls straight into a fixed-length comparison of the next few bytes (the length of the comment-marker string, e.g. two characters for a "//"-style marker) against that marker. That comparison's very first byte read is therefore already one past the end of the buffer, exactly matching the reported "0 bytes to the right of an 18-byte region" 1-byte OOB read. A crafted MD5 mesh file whose final content byte (immediately before the file ends) is an unmatched quote character reproduces this deterministically: the quote-skip loop's last iteration reads the trailing NUL, still advances the pointer past it, and the marker comparison that immediately follows is the one ASan catches.

Note on the recorded fix commit: it does not actually explain this crash. Its diff is a pure brace/whitespace formatting pass with no logic change to the comment-stripping code, and it lands after the real patch, which explicitly closes this exact bug by issue number in two commits: a first attempt that started recomputing, on each scan step, how many bytes remain from the *current* scan position before allowing the marker-length comparison to run -- which its own follow-up commit's message says was "not sufficient to fix the bug" (most likely because the quote-skipping inner loop could still push the scan pointer past the buffer's end before that remaining-length check executed, via an unsigned wraparound that made the just-added check pass anyway) -- followed by a corrected version that replaces the whole scan with an explicit, always-in-bounds index loop, so the quote-skip itself can never run the index past the buffer's length and the remaining-length check is therefore always accurate. The recorded commit is simply the next commit to touch that file after this real, two-commit fix landed, most likely mis-attributed by coarse day-granularity build-snapshot bisection/re-verification rather than by tracing the actual patch.
