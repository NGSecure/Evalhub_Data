matio (ASan/honggfuzz build): while iterating the top-level group of a MAT v7.3 file (matio's own wrapper around the HDF5 container format) to list its variables, the routine repeatedly calls into the linked HDF5 library to look up each entry's object info and, in the process, to protect (load into the metadata cache) the associated object header. On a corrupted input file, an earlier symbol-table local heap and a later object header chunk are already malformed: HDF5 itself detects and logs a long chain of internal errors (an out-of-range heap free list, and twice a header carrying an unrecognized/"bad" version number) but keeps walking the group anyway instead of aborting the whole iteration. When it goes on to protect a header whose declared chunk layout is itself corrupted, the metadata-cache load path ends up computing a bogus pointer/offset into the chunk's raw byte buffer and dereferences it directly, producing a wild-address read segfault deep inside the HDF5 code that matio calls into, rather than in matio's own MAT5/MAT7.3 parsing routines. There is no targeted source-level patch for this bug: the commit that stops the OSS-Fuzz reproducer from crashing only rewrites matio's fuzzing build recipe, replacing the previously system-linked, older HDF5 release with a statically bundled newer HDF5 version that no longer exhibits the defect. In other words, the underlying bug lived in the third-party HDF5 library's own object-header loading code, and the "fix" is a dependency-version upgrade rather than a code change to matio's (or HDF5's) source within this repository.
