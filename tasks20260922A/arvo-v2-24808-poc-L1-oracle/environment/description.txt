RDKit's V2000 molfile-to-mol streaming fuzz target (libFuzzer, UBSan build): an invalid virtual-call/bad-cast fault fires while parsing the optional property-line block of a V2000 CTAB, because a SubstanceGroup member-atom list is populated through a dangling bookmark left behind by an earlier, unrelated property line in the same block. Root cause: the parser resolves each V2000 SGroup vector-data property line's 3-letter tag to one of three sibling handlers -- "SAL" adds an atom to the group's member-atom list, "SBL" adds a bond, "SPA" adds a parent atom -- and all three resolve their integer operand through the same atom/bond bookmark table before immediately reading a field off the returned pointer. If, earlier in the same property block, a Marvin-style SMARTS property line swapped in a brand-new Atom object at an existing atom position, the molecule's in-place atom-replacement helper deletes the original Atom instance but never updates any bookmark that was still pointing at it, so the bookmark table keeps holding the now-dangling raw pointer. When a later "SAL" line in that same block adds one of the group's member atoms by referencing that same stale bookmark, the handler resolves the bookmark back to the already-freed Atom object and immediately reads a field off it -- RDKit's Atom class is polymorphic, so this dereference of freed-and-reused memory is caught as an invalid member call on an object whose vtable pointer no longer identifies it as an Atom, rather than as a plain out-of-bounds read. So the crash requires two property lines to fire in the right relative order within one CTAB block: first one that replaces an atom carrying a live bookmark, then a member-atom-list line that consumes that same bookmark afterward, by which point the object it names has already been destroyed.
