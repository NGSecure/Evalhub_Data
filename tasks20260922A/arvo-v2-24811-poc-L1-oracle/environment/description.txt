libavif's AVIF decode fuzz target (ASan build): decoding a crafted AVIF file whose "grid" derived-image item declares an oversized output width and height triggers a wild out-of-bounds write when the decoder copies each grid tile's pixel rows into the assembled full-size output image, surfacing as a SEGV on an unmapped/wild address inside a row-copy memcpy. Root cause: the grid item's declared output width and height are taken straight from the bitstream as unconstrained 32-bit values, with nothing bounding their product before those values are used both to size the destination image's pixel buffer and to compute each tile's per-row copy offset and stride. When the attacker picks a width/height pair whose product overflows during the destination buffer's allocation-size arithmetic, the buffer that is actually allocated ends up far smaller than intended, but the tile-assembly loop still derives its row byte-offsets from the original, un-overflowed (huge) output width, so successive per-tile row copies walk off the end of the undersized buffer. The public fix closes this by validating, immediately after the grid item's dimensions are parsed and before they are used for any buffer sizing or copying, that width and height cannot combine to exceed a fixed maximum total-pixel-count ceiling — using an overflow-safe division-based comparison rather than multiplying the two values directly — so an oversized grid is now rejected as malformed input at parse time instead of reaching the tile-copy path at all.
