Decompressing a crafted, truncated c-blosc2 compressed buffer through the library's zlib-codec (miniz-based DEFLATE) decompression backend causes a one-byte heap-buffer-overflow READ past the end of the compressed input buffer, aborting under ASan.

Root cause: c-blosc2's block/stream decompression logic derives the length of each per-stream compressed payload from an untrusted 4-byte size field embedded in the (attacker-supplied) chunk header, then hands a pointer into the caller's input buffer, together with that header-declared length, straight to whichever compression codec the header selects; for a zlib-flagged chunk this reaches the vendored miniz DEFLATE decoder through its usual zlib-compatible wrapper calls. Nowhere along this path was the header-declared payload length ever checked against how many bytes of the caller-supplied source buffer were actually still present at that offset. In fact the public decompression entry points did not even carry the size of the caller's own input buffer as a parameter — only a destination-buffer size was passed in — so there was no value on hand to validate the declared length against in the first place. When the header claims a compressed-stream size larger than what the real buffer holds, as a malformed 40-byte fuzzer input does here, the DEFLATE decoder is invoked with a byte count that overruns the actual allocation, and while it walks the compressed bitstream looking for the end of the stream it reads one byte past the tail of the heap block before anything notices the mismatch.

fix_commit assessment: the patch is credible and directly on point for this crash. It threads an explicit input-buffer-length parameter through the entire decompression call chain — from the public context-based decompression/get-item entry points down through the per-chunk dispatch and per-block worker routines — and adds a bounds check at exactly the spot where a per-stream compressed-size field is pulled out of the header and used to step past that stream's payload before handing it to the codec: if consuming the declared payload would run past the end of the available input, decompression now bails out with an error instead of proceeding into the codec call. Equivalent length checks are added at every other place that had been trusting header-derived offsets or counts (the initial short/extended header parse, the per-chunk offsets table, and an optional trailing dictionary block used by one of the other codecs) without ever validating them against the caller-supplied input size. Because the crash is exactly an in-codec over-read caused by a compressed-length value that outran the real input buffer, and the patch's core addition is the missing length check immediately upstream of that same codec call on that same code path, fix_commit is trustworthy as the fix for this bug.
