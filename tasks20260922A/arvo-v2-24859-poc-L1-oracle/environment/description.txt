util-linux's fdisk partition-table library derives an output device-name string for each partition while re-serializing a parsed partition-table script back out (e.g. writing it in sfdisk's plain-text format). To detect one legacy 4-character device-name suffix ("disc"), it takes the device-name string's length, subtracts 4 from it unconditionally, and uses that offset to index directly into the string for a string-equality comparison -- without first checking that the string is at least 4 characters long. Root cause: when the script's device-name value is shorter than 4 characters (as short as a single character, e.g. from a minimal header line naming the device), length-minus-4 goes negative, so the resulting pointer lands a few bytes before the start of the small heap buffer holding that device-name string (itself a heap copy made earlier while the script's header lines were parsed); the ensuing comparison then reads starting at that out-of-bounds address, a few bytes to the left of the allocation, producing a heap-buffer-overflow read. The bug only fires on the write/output path for a parsed script, never while the original input is being read. The upstream fix replaces the raw pointer arithmetic with a length-guarded suffix check that first confirms the string is at least as long as the suffix before comparing anything, so a device-name string shorter than the suffix now safely reports "no match" instead of producing a negative offset -- closing exactly the short-device-name condition that let the offset go negative.
