A bug in The Sleuth Kit's ext2/ext3 file-system module (ASan heap-buffer-overflow, 1-byte read) fires while an `fls`-style recursive directory walk scans a directory's entries for orphaned (unlinked but still-referenced) inodes: for each candidate inode number the code loads that inode's block-group allocation bitmap into a heap buffer sized to exactly one file-system block, then computes the inode's bit offset relative to the group's base inode and checks that offset against the buffer's bit capacity before indexing into it. Root cause: the bounds check uses a strict "greater than" comparison against the bitmap's bit capacity instead of "greater than or equal to", so an inode number whose computed bit offset lands exactly on the boundary (equal to the buffer's total bit count, i.e. one bit past the last valid bit) is wrongly treated as in-range; the code then dereferences the byte holding that out-of-range bit, reading one byte past the end of the just-allocated bitmap buffer. A crafted/corrupted ext2 image that makes some inode referenced during the orphan scan resolve to exactly this boundary offset (e.g. via a bogus/oversized inode number relative to its group) is enough to trigger the read.
