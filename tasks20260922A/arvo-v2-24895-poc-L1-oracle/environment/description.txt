One-sentence summary: Parsing a crafted/corrupted HFS+ (or HFSX) filesystem image with `fls` triggers a 1-byte heap-buffer-overflow READ while the library is loading a file's extended attributes during catalog-entry lookup, because the size of one "node" of the on-disk Attributes B-tree is trusted from the image without being checked against the minimum size needed to hold a node's fixed header.

Root-cause mechanism: when the library first accesses a file's metadata it opens the special Attributes B-tree that HFS+ uses to store extended attributes (including the flags that mark a file as compressed). It reads a 16-bit "node size" value straight out of the Attributes file's own on-disk B-tree header record and stores it unvalidated. That value is then used, unchanged, as the size of a heap buffer allocated to hold one full node's worth of raw bytes, and as the exact byte count requested when reading a node into that buffer from the image. Immediately after the read, the code reinterprets the start of that same buffer as a small fixed-layout node-descriptor structure — forward/backward sibling links, then a one-byte node-type field, then a height byte and a two-byte record count — purely to branch on whether the node is a leaf or an internal/index node before deciding how to continue walking the tree.

Nothing on this path ever confirms that the attacker/corruption-controlled node-size value is at least as large as that fixed descriptor structure. A crafted image can set the on-disk node-size field to an implausibly small value (in the observed crash, effectively 1 byte). The heap allocation and the subsequent read then both use that tiny size, so the buffer holding "one node" is far smaller than the descriptor the code is about to dereference. The very next field access — reading the node-type byte, which lives several bytes past the start of the descriptor layout — lands outside the tiny allocation entirely, walking into the heap's right redzone and producing the reported out-of-bounds read. Because this happens on every attribute-file node visited while walking from the root of the Attributes tree down to a leaf, the same missing check is reachable purely by having any file whose catalog lookup triggers extended-attribute loading, with no other precondition beyond a corrupted/undersized node-size field in that one on-disk header record.

fix_commit assessment: the associated patch is credible for this crash. It inserts a single guard, evaluated right after the Attributes file is confirmed non-empty and immediately before the node-sized heap buffer is allocated, that rejects the on-disk node-size value whenever it is smaller than the fixed node-descriptor structure's size and bails out of the attribute-loading routine with an error instead of proceeding. That is precisely the condition this crash needs: an undersized, attacker/corruption-controlled node size that is later dereferenced as a fixed-size structure. The allocation site and the out-of-bounds field access reported in the crash both live inside the same function this guard was added to, and the small 1-byte-region / 7-bytes-past-the-end signature lines up exactly with "node size below the descriptor's byte offset for the type field" — so the patch closes the exact gap that produced the overflow, not an unrelated one.
