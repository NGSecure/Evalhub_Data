A bug in The Sleuth Kit's NTFS non-resident-runlist decoder causes a 1-byte heap-buffer-overflow read while walking a crafted MFT file-record attribute's data-run list. Root cause: the routine parses each run entry's length field and address-offset field from a shared byte cursor moving through a heap buffer sized to one MFT record, and it correctly rejects a length-field byte-count greater than eight before consuming those bytes — but the analogous sanity check that is supposed to guard the address-offset field's byte-count instead re-inspects the length field's nibble again rather than the offset field's own nibble. A crafted run header can therefore encode an offset-field byte-count larger than eight (and larger than what actually remains in the buffer) while still passing that check, because the wrong half of the run-header control byte is being validated. The unvalidated, oversized offset count lets the parsing cursor be advanced past where it should stop; on the very next iteration of the outer loop, the byte-by-byte read of the following run entry's length field walks the already-overrun cursor one more byte past the end of the heap allocation, which is what AddressSanitizer flags as the out-of-bounds read.
