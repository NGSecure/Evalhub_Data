The Sleuth Kit's HFS+ filesystem support crashes (AddressSanitizer heap-buffer-overflow read) while it is still just opening a crafted HFS+ image: hfs_open() calls a helper that scans the volume's catalog B-tree to find the highest in-use catalog node ID, and that scan is what walks into invalid memory before any higher-level file listing even begins.

The catalog B-tree scan processes an index node by iterating its records. For each record it reads a 16-bit value out of the node's trailing record-offset table and treats that value as the byte offset, within the same node buffer, where a catalog key structure begins. Before using the offset it is checked against the node's declared size, but the check only rejects offsets that are strictly greater than the node size — an offset that is exactly equal to the node size is accepted as "in bounds." The code then forms a pointer at that offset into the node buffer and immediately dereferences it to read the key structure's length field, in order to compute how many bytes the whole key occupies. Because a heap buffer of N bytes only has valid indices 0..N-1, an offset equal to N points one byte past the end of the allocation; the immediate read of the key's length field there touches the first byte of the adjacent redzone, which AddressSanitizer reports as a 1-byte heap-buffer-overflow read. In the observed crash the node buffer was 2570 bytes and the record-offset table entry for the record under examination was crafted to equal 2570 exactly, so the very first field access after the "bounds check" already lands out of bounds — no other corruption (e.g. an offset far beyond the node, or a negative/wrapped offset) is needed to trigger it; a single off-by-one value is sufficient.

fix_commit plausibility: highly plausible. In the exact index-node record-parsing block that performs this offset check and the subsequent key-length read, the fix tightens the comparison from "offset strictly greater than node size is invalid" to "offset greater than or equal to node size is invalid," which precisely removes the off-by-one window that let offset == node-size pass as valid right before the out-of-bounds dereference. The same commit also adds a companion bounds check earlier in the same block, guarding the read that derives the record offset itself (so a too-large record index cannot make that earlier computation wrap/underflow), and it applies the identical pair of fixes to the sibling leaf-node record-parsing block in the same routine and to an analogous record-offset lookup in a related extent-record routine in the same file. Those parallel fixes address the same class of bug in nearby code paths rather than the exact lines this particular crash exercises, but the primary fix — the off-by-one correction in the index-node block — sits precisely on the call path and precisely at the check whose failure produces this crash.
