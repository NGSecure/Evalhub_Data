The Sleuthkit `fls` NTFS fuzz target (ASan build) triggers a 1-byte heap-buffer-overflow read while parsing a crafted MFT record's fixup ("update sequence") header. The record-lookup routine that opens an inode's MFT entry allocates a scratch buffer `a_buf` of exactly `a_ntfs->mft_rsize_b` bytes (512 in this PoC) and hands it to the inner routine that applies the update-sequence fixup, which reads the record's `upd_off` (update-sequence-array offset) and `upd_cnt` (update-sequence-array count) fields and validates them with a single combined bounds check: `upd_off + sizeof(ntfs_upd) + 2*(upd_cnt - 1) > mft_rsize_b`. Root cause: `upd_cnt` is never checked for zero before being used in `upd_cnt - 1`. With a crafted `upd_cnt == 0`, the term `2*(upd_cnt - 1)` evaluates to -2, which exactly cancels out the positive `sizeof(ntfs_upd)` margin the check is supposed to enforce, so the effective condition collapses to `upd_off > mft_rsize_b` instead of `upd_off + sizeof(ntfs_upd) > mft_rsize_b`. This lets a record with `upd_off == mft_rsize_b` (i.e. the update-sequence header sitting exactly at, not before, the end of the 512-byte buffer) pass the check undetected. The code then computes a pointer as `a_buf + upd_off` and immediately dereferences it to read a 2-byte "update sequence number" field — a read that starts exactly 0 bytes past the end of the `a_buf` allocation, which is what AddressSanitizer flags.

fix_commit 4d379cb12e67f5bc690d2e2e4d6ce752c2b41e67 is directly on point: it replaces the single combined check with two sequential ones performed in unsigned `size_t`/`uint16_t` arithmetic — first rejecting `upd_cnt == 0` (and `upd_cnt` too large relative to `mft_rsize_b`) outright before any subtraction involving it can occur, then separately computing the fixup array's reserved size `(upd_cnt - 1) * 2` and checking `upd_off + sizeof(ntfs_upd) > mft_rsize_b - reserved_size` before `upd_off` is ever used to form the fixup pointer. This closes exactly the gap exploited above and directly guards the read that crashes, so the fix is credible and well-targeted; no correction to `fix_commit` is needed.
