sleuthkit's ISO-9660 filesystem module (exercised by the sleuthkit_fls_iso9660_fuzzer AFL/ASan target): a stack-buffer-overflow read occurs while sleuthkit reconstructs inode information from a directory record. Each directory record is copied into a fixed 2048-byte buffer on the stack of the record-loading routine, whose frame also holds two smaller name-conversion buffers (name16/name8) further along; the record's trailing "System Use" area -- one or more length-prefixed System Use Sharing Protocol (SUSP) entries, including the Rock Ridge "NM" alternate/long-name extension -- is then walked in place inside that same 2048-byte buffer. The routine that parses these SUSP/Rock-Ridge entries derives both its own cursor advance and the number of bytes to copy into the reconstructed POSIX name directly from a one-byte length field taken from the untrusted on-disk entry, and it is meant to reject any entry whose declared length would place its data outside the parent record buffer. That bounds test mixes pointer arithmetic against the buffer's end pointer with a length computed as a small signed value (the entry's length field minus the fixed size of the NM entry header); when the on-disk length field encodes a value at or below that header size, the subtraction underflows before the comparison is evaluated, so the too-short/malformed entry is treated as still inside the buffer instead of being rejected. Immediately afterward, the name bytes are copied out of the entry using that same invalid length, and because the length no longer reflects how much real data actually remains in the 2048-byte record buffer, the copy runs off the end of it and continues reading into the surrounding stack memory of the calling frame -- including the space adjacent to the name16/name8 buffers -- well past where the record's real data ends. This is what AddressSanitizer flags as a 944-byte out-of-bounds stack read.
