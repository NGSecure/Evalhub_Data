A heap-use-after-free read occurs in open62541 while constructing a server object, when an allocation deeper in the setup sequence fails partway through. The failing setup path performs its own cleanup and, as part of that, frees the node store's backing context through the store's registered destructor/clear callback. Control then returns to the top-level constructor, whose own error-handling branch is unaware that this cleanup already happened, so it invokes the very same destructor callback a second time on the same, now-dangling context pointer. That second, redundant call dereferences a field inside the already-freed node-store structure, producing the use-after-free read. The condition has nothing to do with the content of any protocol message being parsed: it fires purely from an internal allocation failure during server setup, before any input bytes are consumed, and stems from cleanup responsibility for the node-store context being duplicated between the inner setup routine and the outer constructor's error path instead of being owned by exactly one of them.
