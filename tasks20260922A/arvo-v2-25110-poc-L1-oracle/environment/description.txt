In libxml2's XInclude processor (MSan build), each pending inclusion reference is resolved (its replacement content loaded, or a fallback substituted) and then revisited in a later pass that decides which of those references still need their replacement content actually spliced into the tree. A prior change had turned that decision from a positive test ("does this reference still hold real replacement content, or was its fallback deliberately empty") into a negative one ("was this reference explicitly marked as a total failure"), with the failure marker only ever set for the single case of a load that failed outright with no fallback available at all. Any reference that had already been fully handled through some other path -- in particular one reached through a fallback that itself recursively contains another inclusion -- was never marked, so the later pass still treated it as needing (re-)substitution and dereferenced it again. Because the driving API here is the streaming pull-parser, which proactively frees node structures it no longer needs as it advances through the document, that stale second look-up lands on a node whose backing memory has already been reclaimed by the time the pass runs; reading through it to perform substitution that was in fact already done is what MemorySanitizer flags as a use of an uninitialized value, since sanitizer-poisoned freed memory is indistinguishable from never-initialized memory. The fix drops the failure-only marker and goes back to a purely positive test -- "still has real content to substitute" or "legitimately resolved to an empty fallback" -- so a reference that has already been consumed elsewhere no longer qualifies for re-processing on the later pass.
