Decompressing a crafted, truncated c-blosc2 compressed buffer through the library's context-based decompression entry point causes a one-byte heap-buffer-overflow READ past the end of the compressed input buffer inside the library's vendored zlib-compatible DEFLATE decoder, aborting under ASan.

Root cause: the library's context-based decompression entry point takes an explicit caller-supplied compressed-input-size argument, whose purpose is to let all of the per-block/per-stream decompression logic further down the call chain bound how much of the source buffer it may read before handing a slice of it to whichever codec a chunk's header selects. Along the lock-protected, global-context code path that this entry point normally takes, however, that caller-supplied size argument is silently discarded right before the call into the internal decompression worker: an unrelated, effectively-unbounded placeholder value is substituted for it instead. Because that placeholder is many orders of magnitude larger than any real compressed buffer, every bounds check further down the call chain that compares a header-declared per-stream payload length against "how much of the source buffer is actually still available" ends up being evaluated against the placeholder rather than the buffer's true size, so those checks can never fire on this path no matter how small the real input is. When a crafted, truncated header claims a zlib/DEFLATE-compressed sub-stream that is longer than the tiny real input actually holds — as the roughly 40-byte fuzzer input does here — the vendored DEFLATE decoder is invoked believing it has far more input available to consume than truly exists, and while it walks the compressed bitstream looking for the end of the stream it reads one byte past the tail of the real heap allocation before anything notices the mismatch.

fix_commit assessment: the patch is a minimal, surgical one-line correction that is directly on point for this crash. At exactly the call site inside the lock-protected decompression entry point that hands control to the internal decompression worker, it replaces the unrelated, effectively-unbounded placeholder value with the caller's actual compressed-input-size argument — the same argument that was being silently dropped — so the bounds-checking machinery already present further down the call chain now evaluates header-declared stream lengths against the real buffer size instead of an oversized stand-in. No other lines change. This lines up precisely with the crash mechanism: the over-read happens because a per-stream length check downstream of this call site was trivially satisfied against the wrong (oversized) bound, and forwarding the true size is exactly what makes that check meaningful again for this code path. fix_commit is trustworthy as the fix for this bug.
