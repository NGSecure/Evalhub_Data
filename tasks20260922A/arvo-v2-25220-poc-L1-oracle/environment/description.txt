RDKit's V3000 molfile-to-mol streaming fuzz target (libFuzzer, MSan build) raises a use-of-uninitialized-value warning while parsing a count-prefixed, parenthesized list of unsigned integers embedded in a V3000-format substance-group (SGroup) definition (e.g. a list of member atom or bond indices attached to the group). A shared parsing helper used for this kind of array field reads the leading count token directly off the input stream into a plain local unsigned integer that is declared without any initial value, on the assumption that the stream extraction will always run to completion and leave a legitimately parsed number behind. When the array field in the input is malformed enough that the count token cannot be extracted cleanly -- for instance when the expected opening delimiter or the count digits themselves are missing, truncated, or non-numeric -- the stream's extraction operator can fail without ever writing anything into the destination variable, leaving it holding whatever indeterminate bit pattern already occupied that stack slot from an earlier call. The parser immediately uses this never-actually-initialized value to size a reserve() call for the vector about to hold the array's elements, and it is at that point -- before a single array element has even been read -- that MemorySanitizer flags the read of indeterminate stack contents. No heap corruption, out-of-bounds access, or freed memory is involved; the bug is purely a missing default initializer on a local variable whose value is expected to come from a stream extraction that the code never checks for success.
