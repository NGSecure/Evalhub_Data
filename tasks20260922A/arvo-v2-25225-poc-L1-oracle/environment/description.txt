RDKit's V3000 molfile-to-mol streaming fuzz target (libFuzzer, MSan build) raises a use-of-uninitialized-value warning while parsing an attachment-point sub-field of a V3000-format substance-group (SGroup) definition, which is expected to carry a short fixed sequence of tokens: a leading count, an atom index that anchors the attachment point to an existing atom via that atom's bookmark id, and a couple of trailing string identifiers. All of these fields are pulled off the input stream in a single chained extraction into local variables that, like a sibling array-parsing routine elsewhere in the same file, are declared without any initializer of their own, on the assumption that the whole chain will run to completion. When the input line is truncated partway through -- e.g. it supplies the leading count token but not the atom-index token expected to follow it -- the extraction for that missing field fails without writing anything into its destination variable, leaving the atom-index variable holding whatever indeterminate stack contents were already there. The parser then immediately hands that never-actually-initialized value to the molecule's bookmark-based atom-lookup facility (the same general mechanism that lets one part of a molfile refer back to an atom introduced under a numbered marker earlier in the file) to resolve it to an existing atom. That lookup consults an associative container keyed by the bookmark id, and it is several stack frames deep inside that container's ordinary comparison/traversal logic -- not at the line that actually failed to initialize the variable -- that MemorySanitizer catches the indeterminate bits being consumed as a search key. The crash-reporting frame and the actual defect therefore sit in two different functions: the associative lookup itself is only relaying a bad key it was handed, and holds no bug of its own.
