When PcapPlusPlus parses a DNS resource record out of a packet, it decompresses the record's on-wire name into a fixed 256-byte stack buffer and then hands that buffer to a C++ string's assignment operator as if it were an ordinary NUL-terminated C string; a crafted DNS message can make that assignment crash with a wild write deep inside the string implementation instead of just producing a normal string. Root cause: the name-decompression routine tracks, across the run of labels it has processed so far, how many bytes of output it has already produced, and is only supposed to keep writing into the 256-byte buffer while that running count still leaves room; but when a sequence of ordinary (uncompressed) labels happens to fill the buffer to exactly its capacity, and the very next label turns out to be a compression pointer to another location earlier in the same message, the routine still follows that pointer and recurses to decode the name it references, without first checking whether the destination buffer has any headroom left at all. The step that would copy the pointed-to name's characters into the buffer correctly does nothing in this situation (its own remaining-space guard is already exhausted), but the line meant to place the terminating NUL still runs unconditionally through the current write cursor — which by then sits exactly one byte past the end of the 256-byte array — so the NUL lands just outside the buffer instead of inside it, leaving the buffer itself entirely without an in-bounds terminator even though it is completely full of real name characters. The string-assignment call that follows has no idea its source is a bounded fixed-size array: it scans forward hunting for a terminator, runs off the end of the stack buffer into unrelated memory, eventually finds some incidental zero byte far away and treats the distance to it as the string's length, then crashes while copying that bogus, oversized length into the destination string's storage.

Fix-commit assessment: the patch touches exactly this compression-pointer branch and adds a check that rejects following the pointer once the accumulated output length has already reached the buffer's capacity boundary, forcing an early, safely-bounded return instead of falling through to the unconditional terminator write — this directly closes the gap described above (the same file's other edits, brace-style reflow and the accompanying regression-sample addition, are cosmetic/test-only and don't change behavior elsewhere). Unlike the earlier PcapPlusPlus id 22837 in this batch series, where the recorded fix left the crashing code path untouched and the diff amounted to unrelated day-bisection churn, here the mechanism traced from the crash backtrace lines up precisely with the condition the patch adds, so the fix_commit is judged credible for this differential.
