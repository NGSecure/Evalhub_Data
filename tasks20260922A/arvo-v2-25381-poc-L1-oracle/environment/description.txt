uWebSockets' publish/subscribe topic-tree fuzz target (ASan build): when all of a client's subscriptions are torn down at once, the library prunes topic nodes left with no subscribers and no children out of the tree. Pruning a node that still had a pending notification requires filtering it out of the shared pending-notification array, and the implementation does this by copying every other still-pending entry into a fresh, fixed 64-slot array allocated on the stack. Because a separate missing capacity check elsewhere in the same subsystem can let the shared count of pending entries silently grow past 64 before this pruning ever runs, the filtering copy loop -- which trusts that count as its iteration bound -- ends up writing more than 64 entries into the 64-slot stack array, overflowing it and corrupting adjacent stack memory (an 8-byte write caught by the stack canary/redzone).
