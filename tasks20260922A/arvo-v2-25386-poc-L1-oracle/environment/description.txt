rnp's KBX keyring loader trips a 1-byte heap-buffer-overflow READ while decoding the mandatory first "header" blob of a .kbx keyfile.

Root cause: the first blob of a KBX file is a fixed 32-byte structure (a short generic blob header, a 1-byte version, a 2-byte flags field, a 4-byte "KBXf" magic string, and a run of 4-byte reserved/timestamp fields), and the parser walks it sequentially with a single cursor pointer, advancing the cursor by each field's width as it goes. Two independent mistakes in that walk combine to push the cursor past the end of the 32-byte buffer before the overflow read actually happens: (1) after validating the 4-byte "KBXf" magic string, the cursor is advanced by only 3 bytes instead of 4, permanently misaligning every field read that follows by one byte; and (2) immediately after correctly decoding one of the 4-byte big-endian integer fields at the (already misaligned) cursor and advancing past it, the very same field is decoded a second time from that new cursor position but with an extra, unexplained +15-byte offset added on top, instead of simply continuing the sequential walk to the next field. That second, spurious decode is what actually reads out of bounds: the +15 displacement lands the 4-byte big-endian reader helper 2 bytes beyond the end of the 32-byte header buffer, and the first byte it reads there is the one AddressSanitizer flags. The blob's declared length is checked up front against the expected 32-byte constant, but nothing checks the field-by-field cursor arithmetic against that length as parsing proceeds, so any input whose leading blob-type/length pair passes the top-level size check reaches this stray read deterministically, independent of the actual field contents.

fix_commit assessment: credible / directly on point. The patch touches exactly this header-blob parsing routine and: (a) fixes the magic-string skip to advance the full 4 bytes instead of 3, and (b) deletes the duplicated second decode-with-+15-offset statement entirely, leaving a single correct sequential read of that field. It also hardens an unrelated but adjacent blob-type dispatch (switching from computing a struct size per-branch-then-checking-null to a single centralized allocation-size variable) and switches a case-insensitive string compare to a plain memory compare for the magic check — neither of those two extra changes is what the reported crash needed, but the two fixes described above precisely close the exact misalignment (mistake 1) and the exact spurious out-of-bounds decode (mistake 2) that this crash trace shows, and the accompanying regression test embeds the literal oss-fuzz issue number for this bug and the exact crashing input as a new fixture. There is no reason to doubt this fix_commit.
