muparser (ASan build, set_eval_fuzzer target): evaluating an expression built from a long list of comma-separated top-level sub-expressions, where most items are parenthesized empty/whitespace string literals but the very last item is a plain numeric literal, triggers an 8-byte heap-buffer-overflow read from the interpreter's per-thread evaluation stack. Root cause: after compiling an expression, the parser runs a sanity check meant to reject "multi-value" expressions whose comma-separated results are not all numeric, but that check only inspects the type of the single most-recently-compiled sub-result (i.e. the last comma item) instead of every sub-result collected while compiling the whole expression; a numeric literal placed after a long run of string-literal items therefore lets the check pass even though almost every other comma-separated item actually evaluated to a string. Separately, a standalone parenthesized string literal never emits any instruction into the compiled bytecode stream at all (it is recorded only in an auxiliary string table used purely at compile time), unlike a numeric literal or variable reference, each of which appends one bytecode instruction and advances a running high-water-mark that the evaluator later uses to size its runtime result buffer. Because most of the crafted expression's comma items are such no-instruction string literals, the compiled bytecode stream ends up far shallower than the actual number of comma-separated items, so the high-water-mark-derived buffer is allocated far smaller than the index that is later used to fetch the expression's "final" result -- that index is simply the total count of comma-separated items, not anything derived from the bytecode. Evaluating the compiled expression then indexes into the undersized buffer at that too-large index, reading 8 bytes past the end of the heap allocation.
