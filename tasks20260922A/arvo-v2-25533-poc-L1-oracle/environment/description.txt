htslib (ASan build): while validating a BCF (binary VCF) record during header/record sanity-checking, a shared "typed integer" decoding helper bounds-checks how many bytes remain in the record's buffer before performing a little-endian load of the encoded integer, but it compares the remaining-byte count directly against the small internal shift/log2 code that identifies the integer's storage width rather than against the actual byte width that code represents. Root cause: for any encoded width wider than a single byte (e.g. a 4-byte, 32-bit field) the real requirement is several times larger than the shift value being compared against, so the check is satisfied while only two-or-so bytes remain even though the subsequent load reads four; on a truncated/corrupted record whose remaining buffer happens to fall just short of that true requirement, the load walks past the end of the heap allocation backing the record and the read lands in unmapped/red-zoned memory. The fix recomputes the required byte count as two raised to the power of the shift code (i.e. the real width) instead of using the shift code itself, so the bounds check now demands exactly as many trailing bytes as the load will actually consume, for every multi-byte integer width the decoder supports.
