libucl's UCL config parser triggers a heap-buffer-overflow READ while building an error message for a config-inheritance failure (the case where an object referenced through UCL's "inherit from ancestor" syntax cannot be found, or resolves to something that is not itself an object). Root cause: the code path that formats that particular error message passes a malformed printf-style conversion specifier to the variadic error-formatting helper. The call intends a bounded copy of a non-NUL-terminated byte range straight out of the parser's input buffer -- a length paired with a pointer into that buffer, meant to be interpreted as "copy at most this many bytes from this pointer" -- but the conversion specifier's field order is wrong, so the length argument does not end up wired to the copy-bound (precision) role at all; instead it is consumed as an unrelated display-width value, and the string conversion is left with no effective bound tying it to the caller-supplied length. Because the pointed-to bytes are a raw slice of the input buffer rather than a NUL-terminated C string, the printf-family machinery that resolves how far a %s argument extends (AddressSanitizer's own format-string-driven interceptor, which validates the memory a printf-like call is about to touch before the real implementation runs) ends up probing past the end of the actual input allocation looking for where the string "ends," walking a few bytes into the heap redzone immediately following that (small, exactly-sized) buffer. Correcting the conversion specifier so the length argument is genuinely wired to the copy-bound (precision) role restores a read strictly confined to the caller-supplied length and removes the over-read.
