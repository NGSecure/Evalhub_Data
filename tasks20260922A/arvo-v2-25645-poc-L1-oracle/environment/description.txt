A bug in The Sleuth Kit's NTFS MFT-record loader lets a crafted file record disable an on-disk integrity/restore mechanism entirely, which later causes a 1-byte heap-buffer-overflow read while a data attribute's non-resident run list is decoded. Background: each raw on-disk MFT record has, by NTFS format design, its last two bytes of every 512-byte sector temporarily overwritten with a signature value; the true original bytes are stored elsewhere in the record and are supposed to be verified against that signature and copied back before the record is parsed any further. The record also declares, in a small header field, how many such per-sector entries it contains and where the recovery values start, and the loader is supposed to bounds-check that declared count/offset pair against the record's total size before trusting it. Root cause: the bounds-check arithmetic is not safe against a declared entry count of zero — subtracting one from a zero count feeds a value into the size comparison that lets the check pass instead of rejecting the record — and, independently, the verify-and-restore loop that walks the per-sector entries is itself driven by that same count, so a declared count of zero also makes the loop run zero times regardless of the bounds check's outcome. The combination means a record that declares zero recovery entries sails through validation without ever having its sector-ending bytes checked or restored, leaving those two bytes per sector holding whatever raw value is present in the crafted record instead of the legitimate recovered data. Those un-restored bytes are exactly the bytes subsequently consumed by the routine that walks the attribute's run list one byte at a time: it reads a run-header control byte and derives, from it, how many following bytes encode the run's length and offset, then advances its cursor by that amount before repeating. The crash requires one of the record's two never-restored, sector-ending bytes to land on exactly the last byte of the record's heap allocation; when the parsing cursor reaches that byte, the attacker-controlled leftover value there is read as if it were a legitimate run-header control byte, and because that byte's low nibble (declaring the run's length-field size) is non-zero, the loop immediately reads the very next byte in memory — the first byte of that same run's own length field, laid out directly after the header byte — which lies one byte past the end of the allocation, which is the out-of-bounds read AddressSanitizer reports. The fix rewrites the declared-count/offset bounds check with arithmetic that is safe against both a zero count and an excessively large one, and explicitly rejects a record that declares zero recovery entries, so a malformed record like the crafted one is now rejected as corrupt before any of its raw bytes reach attribute parsing.
