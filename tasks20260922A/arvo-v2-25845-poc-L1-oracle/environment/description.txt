A crafted UDP/QUIC packet can make nDPI's parser for the CHLO ("Client Hello") tag directory accept a tag whose effective length is far larger than the bytes actually available - not because the length is simply left unchecked, but because the bounds check meant to reject an out-of-range tag is itself computed with 32-bit unsigned arithmetic that overflows. The walker sums the tag-table size, the running data offset, and the current tag's declared length to decide whether that tag's data still fits inside the available crypto-data region; when the attacker sets an extreme offset value inside the tag table, that sum wraps past 2^32 and comes back as a small number, so the fits-inside-the-buffer check spuriously passes even though the real, unwrapped length is nowhere close to fitting.

The tag walker then hands the wrapped-but-still-oversized length, together with a pointer into the packet, to the HTTP layer's User-Agent handling routine for the one tag it recognizes as carrying a user-agent-like value. That routine's length parameter is only 16 bits wide, so the huge 32-bit length gets truncated on the call - but the truncated value can still be much larger than the bytes actually left in the buffer at that pointer. The routine allocates a small heap buffer sized to (this length + 1) and then performs a bounded copy using that same untrusted length as the byte count, reading from the tag's data pointer for that many bytes.

Because it is the copy's source-length count that is wrong, not the destination buffer's size, the copy walks straight off the end of the underlying packet buffer while reading; the destination write itself never overflows. This matches the report exactly: it is a READ (not write) overflow inside a strncpy-family call, of size ~956 bytes, whose faulting address sits precisely 0 bytes past the end of a 1280-byte heap region - i.e. the very packet buffer handed to the fuzz target - rather than deep into unrelated heap memory. Landing exactly at that tail edge is the fingerprint of an over-long copy count reading past a buffer it was only ever a few hundred bytes away from the end of, which is consistent with an integer-overflow-defeated bounds check rather than a complete absence of any check.

Note on the recorded fix commit: the associated patch does not touch the QUIC parser or the HTTP module at all - it exclusively adds a new TCP-segment reassembly/fragmentation-buffering subsystem gated behind a new build flag, none of which is reachable from this UDP/QUIC code path or has any bearing on the tag-length validation described above. The recorded fix_commit does not appear to address this crash; it is very likely mismatched/incorrect for this vulnerability id.
