The Sleuth Kit's HFS+ filesystem support crashes (AddressSanitizer heap-buffer-overflow read of 1 byte) while `fls` is opening a crafted HFS+ image and resolving an inode by walking the volume's on-disk catalog B-tree: hfs_inode_lookup() -> hfs_cat_file_lookup() -> hfs_cat_get_record_offset() descend into the catalog B-tree looking for a specific catalog record, and the crash happens on the very first index node visited during that descent, before any leaf-level key data is even touched.

Each B-tree node ends with a trailing table of 16-bit record offsets, one per record, stored in reverse order counting back from the end of the node buffer: to find the byte offset of record `rec`, the code computes an index into the node buffer as (node size) - (rec + 1) * 2 and reads two bytes from there. That subtraction is performed without first checking whether (rec + 1) * 2 can actually be larger than the node's declared size. When a crafted image supplies a record index large enough that (rec + 1) * 2 exceeds the node size, the subtraction underflows: since the node size is an unsigned/pointer-sized quantity, the resulting "index" wraps around to a value that in practice lands just outside -- one byte before the start of -- the just-allocated node buffer (in the observed crash, a 255-byte heap allocation). The immediate read at that wrapped index touches the heap redzone one byte to the left of the buffer, which AddressSanitizer flags as a 1-byte heap-buffer-overflow read. No other node content needs to be corrupted; a single over-large record index recorded in the node's own header is sufficient to trigger it, and it happens before any bounds check on the *value read* from this location even runs -- the existing validation only ever checked the offset value obtained from the read, never the location of the read itself.

fix_commit plausibility: highly plausible, and precisely on-target rather than merely file-adjacent. The commit inserts a new guard -- "if the record's computed table position would exceed the node size, bail out with an error" -- immediately before this exact record-offset read, in the exact branch of the routine that processes index-node records during a B-tree descent. That is, it validates the record index itself before it is ever used to compute a buffer offset, directly closing the underflow this crash exercises. The same commit also tightens a *downstream* comparison in the same branch (the separate check that validates the 16-bit value obtained *from* this read, changing "strictly greater than" to "greater than or equal to") and reapplies both the new pre-read guard and the tightened downstream comparison to the sibling leaf-node-record branch of the same routine and to an analogous record-offset lookup in a related extent-record routine in the same file. Those sibling edits patch a related but distinct off-by-one bug in nearby code (that second bug is the subject of a separate ARVO crash sharing this same fix commit, triggered a few statements further down in the very same branch, once a record offset equal to the node size is wrongly accepted as in-bounds); the specific new guard that maps onto *this* crash's exact read is the first one added, sitting directly on this crash's call path and directly in front of the operation that actually reads out of bounds. No Java-bindings code is touched anywhere in this fix -- the entire diff is confined to native B-tree/extent-record node-parsing code in this one file, in the very routine (and its two structurally identical neighbors) that this crash's call stack passes through.
