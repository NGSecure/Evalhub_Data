Apache Arrow's Parquet-to-Arrow reader crashes on a malformed "version 2" data page whose values are compressed with the Brotli codec, but the crash is not a straightforward overrun in Arrow's own code — it surfaces several call frames deep inside the project's bundled, third-party Brotli decompression library, and the sanitizer reports it as a negative-size parameter passed to a copy routine rather than an ordinary buffer overrun. The page-decode path for a V2 page always begins the same way regardless of codec: it copies the page's uncompressed definition/repetition-level payload — whose combined byte length comes straight from two attacker-controlled 32-bit header fields, unchecked against anything else in the page — out of the raw page bytes and into the front of a working buffer sized from a separate header field that declares the page's total uncompressed size. For this particular crash, that initial level copy itself lands entirely inside the allocated working buffer without incident. The reader then has to hand the *remainder* of that same working buffer to the actual codec, and computes how much of it remains by subtracting the combined levels byte length from the declared total uncompressed size. When a crafted header makes the levels byte length a few bytes larger than the declared uncompressed size, that subtraction underflows a signed integer into a small negative value. That negative value is passed, through several layers of Arrow's own codec-selection glue, into the Brotli library's public decompress entry point as an ordinary remaining-byte count; Brotli's internal decoder state machine eventually reinterprets it as an enormous count inside one of its low-level output-copying routines and attempts a copy against it, which the sanitizer flags immediately because the size argument itself is already negative, before any actual out-of-bounds memory access occurs. This path only executes once genuine codec decompression is invoked, so triggering it requires a page that is specifically declared as Brotli-compressed, and it depends on the *uncompressed*-size header field rather than the compressed one — unlike a related defect in this same code region that instead corrupts the very first, codec-independent level copy and fires unconditionally before any codec runs. The fix adds a single guard, evaluated before either copy executes, rejecting the page whenever either of the header's declared compressed- or uncompressed-size fields is smaller than the declared combined levels length, closing exactly this underflow alongside the sibling one.
