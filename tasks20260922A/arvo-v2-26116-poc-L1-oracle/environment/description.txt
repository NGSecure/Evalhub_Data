OpenSC's Oberthur PKCS#15 card-emulation driver (ASan build, reached through the PKCS#15 bind fuzz target's synthetic-driver path): once a raw on-card elementary file has been read into a freshly allocated heap buffer whose size is simply the file's reported byte length (nothing upstream requires that length to be a multiple of any fixed record width), the routine that decodes that buffer's private-key/data-object directory walks it in fixed 5-byte record steps, using only "is the current record's start offset still less than the total buffer length" as the loop's bound check. Once inside an iteration, if the record's leading marker byte equals the expected sentinel value, the body unconditionally reads four more bytes from that record — a two-byte identifier field and a two-byte size field — without separately checking that all four of those bytes are still within the buffer. When the buffer's total length is not an exact multiple of five, the final iteration starts on a short trailing remainder that actually holds fewer than five bytes; if that remainder's very first byte happens to equal the marker value, the identifier/size reads walk past the marker byte and off the end of the heap allocation, landing one or more bytes into unallocated memory. Because the reported EF size is fully attacker/PoC-controlled (it comes straight from the card's file-size attribute, with no divisibility-by-five check enforced anywhere before the buffer is allocated or parsed), any buffer length that leaves a 1-to-4-byte remainder, combined with a marker byte planted at that remainder's first position, is sufficient to trigger the out-of-bounds read — a loose, easily-satisfied trigger condition rather than a narrow edge case, consistent with this driver's broader pattern of trusting card-supplied lengths without validating them against the actual buffer bounds.

Fix-commit relevance: the patch tightens the loop's bound check in exactly this function, from "current offset is still less than the buffer length" to "current offset plus a full five-byte record still fits within the buffer length" — i.e. it refuses to enter the loop body at all for a trailing remainder shorter than one full record. This directly and precisely closes the read described above; the fix is unambiguously on-target for this crash (same function, same loop, same off-by-N mechanism), not a coincidental or unrelated commit.

Caveat on triggering strictness: as with several other OpenSC parsers in this driver family (permissive, minimally-validated card-data decoders), the precondition here is not tight — no card-specific structural validity is required beyond (a) reaching this emulation path and (b) an EF whose length isn't a clean multiple of five with a marker byte at the tail. Actual exploitability/PoC-construction difficulty for this benchmark task should still be confirmed empirically rather than assumed from this description alone.
