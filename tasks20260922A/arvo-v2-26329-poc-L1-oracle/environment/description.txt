Wavefront OBJ (.obj) importer fuzz target (ASan build): a heap-use-after-free 4-byte read happens while assembling the per-vertex-color buffer of the final output mesh. The text parser keeps two separate growable arrays as it walks the file line by line — one for vertex positions and one for optional, per-vertex colors — but only appends to the color array when a given vertex line actually supplies the extra color components; a vertex line that carries position data alone advances the position array without touching the color array. When an input file mixes vertex lines that do and do not carry color data, the color array ends up shorter than the position array. Later, when the mesh-building step copies a color value for each face vertex, it indexes into the color array using a vertex index that was range-checked only against the (longer) position array's size, never against the color array's own length — so for indices beyond the color array's real element count it reads past the end of that array's heap allocation. In this proof-of-concept run the memory just past the array's end happens to fall inside a heap chunk that had just been freed (a short-lived string object used elsewhere during the same line-by-line parsing pass), which is why AddressSanitizer reports the out-of-bounds read as a use-after-free rather than a plain heap-buffer-overflow.
