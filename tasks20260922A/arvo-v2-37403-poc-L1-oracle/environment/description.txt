nginx (ASan build), http_request_fuzzer: tearing down a request whose body was being proxied to an upstream can re-enter its own teardown routine. The routine that runs a request's registered per-request cleanup callbacks and then destroys the request's memory pool is walking that callback list when it invokes the upstream module's own cleanup callback. That callback drives the request through finalization, upstream finalization, and a lingering-close path that ends up invoking the very same per-request teardown routine again for the same request — and this inner, reentrant call is the one that actually runs the pool-destruction step, freeing all memory allocated from that request's pool. Control then returns to the outer call, which is still in the middle of walking the callback list and advances to the next node by dereferencing a pointer field belonging to a callback-list entry that lives in the pool just freed by the inner call. That dereference is the crash: an 8-byte read of a stale pointer in already-freed memory, not a write, and not a buffer growth/shrink issue — the freed 24-byte block is the callback-list entry the upstream module had allocated for itself when it attached to the request, and the bug is that the outer loop has no way to notice the pool disappeared underneath it during the nested call.
