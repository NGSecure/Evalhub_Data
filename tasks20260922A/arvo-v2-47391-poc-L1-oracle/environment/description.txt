Summary: A crafted BJData (binary-JSON) input parsed by the nlohmann JSON library triggers a 1-byte heap-buffer-overflow READ (a dangling/out-of-bounds read at the boundary of a freed heap region) while decoding an optimized/typed container.

Root cause: When the BJData reader parses an optimized (typed) container, including the size fields of an N-dimensional array, it reads the element-count/size as a *signed* integer but never checks that it is non-negative before use. A negative count is cast directly to std::size_t (yielding a huge unsigned value) and drives the size-parsing logic, which repeatedly appends parsed values into the internal std::vector of JSON values used to hold the container/dimension data. That runaway growth forces the vector to reallocate its backing storage, and the old 16-byte buffer is freed while references/pointers into it are still live. Parsing then continues into the enclosing object and performs a map lookup by key; the object element's std::string key still points into the freed buffer, so the key comparison dereferences the dangling pointer and reads one byte past (to the right of) the freed region — the overflow READ reported by ASan.

Direction check: the mis-handled value is an input-controlled size/count that is signed and negative; treating it as an unsigned size makes the parser over-grow an internal vector, causing a reallocation that invalidates a still-referenced element (its key string), and the fault is a READ of that stale string, not a write.

Fix: the patched reader rejects a negative count in an optimized container up front (parse error 113, "count in an optimized container must be positive") before it can be cast to std::size_t and used, and also short-circuits a zero-sized N-dimensional array dimension to an empty container. This removes the negative-size path that led to the over-growth and the resulting dangling-key out-of-bounds read.
