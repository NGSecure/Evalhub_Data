Summary: A crafted zip archive triggers a 1-byte heap-use-after-free read in libzip during the TorrentZip consistency check performed while opening the archive.

Root cause: When the central-directory comment carries a TorrentZip signature, libzip validates the stored CRC by building a windowed source over the archive data (via _zip_source_window_new) and then wrapping that windowed source in a layered CRC-verification source (via zip_source_crc_create). In libzip a layered source takes ownership of its underlying source: zip_source_layered_create simply stores the underlying source pointer in the new source's `src` field, and freeing the layer later recursively frees whatever it wraps. The vulnerable code, however, calls zip_source_free on the windowed source immediately after successfully wrapping it, even though the newly created CRC source still holds a pointer to that now-freed object. When the CRC source is subsequently opened, opening a layered source recursively opens its underlying source and reads the underlying source object's `source_closed` flag — a read from the already-freed 88-byte source struct, producing the heap-use-after-free (READ of size 1) reported by AddressSanitizer.

Fix: The patch removes the premature zip_source_free call on the windowed source in the success path, so ownership stays with the CRC layer; the windowed source is then released exactly once, recursively, when the CRC source is freed at the end of the check. The error paths (allocation failure of the CRC source) still free the windowed source, which is correct because no layer took ownership of it there. The fix_commit matches the crash: it edits precisely the TorrentZip-check function that both allocates and prematurely frees the windowed source, which is the function on the allocation and free stacks of the ASan report.
