A honggfuzz/ASan run of libjpeg-turbo's turbojpeg transform fuzz target reports a bad-free: AddressSanitizer aborts because free() is called on an address that is not the start of any malloc-ed block, landing just past the end of one of the fuzz harness's own output buffers. This bad pointer surfaces while the transform call finishes decompression and the library's own allocator tears down the pools of memory it tracks internally for the current image; that teardown path is what dereferences the corrupted pointer and hands it to free().

Root cause: the crafted JPEG drives the decoder down a lossless decode path with a data precision above the ordinary 8 bits (12- or 16-bit-per-component samples) while also requesting post-decode color reduction/quantization, or a combined chroma-upsample-plus-colorspace-conversion step. Those two post-processing stages were written assuming ordinary 8-bit sample ranges and use decoded sample values directly as table/array offsets without first clamping them to the valid range. With 12/16-bit lossless samples the computed offsets can run far outside the intended bounds, so the resulting write lands outside its target array and corrupts nearby heap bookkeeping data that the allocator uses to track its own memory pools. When the pools are later torn down, the allocator follows this corrupted bookkeeping and passes a bogus pointer to free(), which is what AddressSanitizer flags as the bad-free.

Direction/variable: this is an out-of-bounds *write* (not a read) that overruns an internal array/table during the color-reduction/upsample step; the corrupted data is allocator-internal linked-list state, not the fuzz harness's own buffer — that buffer's address merely sits adjacent to the corrupted region in the heap layout, which is why the invalid pointer resolves just past its boundary. The invalid free is a downstream symptom, not the original overflow site.

fix_commit judgment: matches. The patch removes color-reduction/quantization support entirely for lossless decompression (for both 12-bit and 16-bit precision) and disables the combined chroma-upsample/colorspace-conversion path for lossless images as well, replacing both with an explicit "not implemented" error instead of running the unclamped, sample-value-driven arithmetic. That eliminates exactly the code path whose out-of-range offsets caused the heap corruption described above, so the fix directly addresses this crash's mechanism.
