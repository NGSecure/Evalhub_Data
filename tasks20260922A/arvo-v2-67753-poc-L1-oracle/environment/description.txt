Summary: An out-of-bounds (wild-address) read in LibRaw while parsing the Adobe RAF makernote of a crafted Fuji TIFF file causes a SEGV under AddressSanitizer.

Root cause: During TIFF IFD parsing, LibRaw::parseAdobeRAFMakernote() (src/metadata/fuji.cpp) reads values from a bounds-checked byte buffer via that buffer's 4-byte read helper (checked_buffer_t::sget4), which ultimately dereferences the buffer through the static big/little-endian reader in src/utils/read_utils.cpp. The offset used for the read is derived from attacker-controlled makernote/header fields and can become negative. The buffer's offset validation only rejected offsets that were too large (offset greater than or equal to the buffer length) and did not reject negative offsets, so a negative offset passed the check unchallenged. The read helper then computes (buffer base pointer + negative offset) and reads 4 bytes from an address located before the start of the buffer, producing the wild-address read / SEGV. This is a read, not a write, and the fault comes from the offset going below zero (underflow of the lower bound), not from it exceeding the buffer length.

Fix: The patch (commit 73d6daa053e1537e29b28eca9b34ab802fdd06e1) hardens the buffer's offset-bounds check by adding a lower-bound test (rejecting off < 0 in addition to off >= _len) so that any negative offset now throws LIBRAW_EXCEPTION_IO_EOF instead of being dereferenced.

fix_commit judgment: The fix_commit matches the crash. The crash path is parseAdobeRAFMakernote -> the buffer's sget4 -> the static reader, and the crashing frame just above the read helper is the buffer's offset-validation/read wrapper. The added "off < 0" guard directly closes the exact condition that produced the wild read (a negative offset that the old check let through). Note: crash.json lists fix_functions as the 2-byte sibling reader, but both the 2-byte and 4-byte read helpers share the same offset-validation routine that the patch actually modifies, so the fix covers the sget4-driven crash as well; the discrepancy is a hunk-attribution artifact, not a sign of a wrong commit.
